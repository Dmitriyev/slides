# Хранение проекта и контекст агента

Реализован один версионированный JSON-проект. Сейчас запись хранится в существующем `slide-tuner.projects.v1` в localStorage. Старые записи автоматически получают `service`; исходный ключ сохранён для миграции истории. Резервная копия включает служебные данные.

| Поле | Содержание | Передача в чат |
| --- | --- | --- |
| `id`, `name`, `updatedAt` | Идентификатор, название, время изменения проекта | Не нужны модели |
| `description` | Первоначальный бриф | Входит в исходный материал |
| `deck.source` | Бриф и извлечённые тексты документов | `source`, полностью |
| `deck.title`, `deck.slides` | Текущая видимая версия; стабильные ID, текст, графики, фиксация, настройки | `current`, полностью |
| `settings`, `selected` | Положения ползунков и выбранный слайд | `settings`, `slide_id`, `scope` |
| `service.schemaVersion` | Версия формата служебных данных: 2 | Не нужна модели |
| `service.revision` | UUID ревизии содержания | Локальная проверка актуальности результатов |
| `service.base` | Каноническое содержание этой ревизии без копии source | Основа генерации альтернатив |
| `service.variants[]` | Ключ, область, ID слайда, настройки и полный альтернативный текст | `alternatives`, все сохранённые варианты |
| `service.messages[]` | Последние 20 сообщений: роль + текст | Предыдущие сообщения + отдельный новый запрос |
| `service.history[]` | До 10 предыдущих состояний содержания, без копий source | Используется для отмены |

Не прячем альтернативы в промпте или примечаниях слайда. Это самостоятельные структурированные данные с полным текстом. Например, агент может найти в `alternatives` простой краткий вариант и использовать его для правки текущего слайда. Исходный материал хранится один раз; в базовой версии, вариантах и истории его копий нет.

## Девять ближайших вариантов

У четырёх ползунков по три уровня: полный перебор — 81 сочетание. Предзагружается окрестность из девяти: текущие настройки и по два других положения каждого ползунка. После смены настроек окрестность пересчитывается; общие готовые варианты переиспользуются. Это не полная матрица 3×3 двух выбранных ползунков.

Сначала пользователь получает исходную презентацию. Через 700 мс покоя начинаются до двух фоновых запросов одновременно. Если настройки совпадают с базовой версией, она используется без запроса модели. Кэш содержит до 18 последних вариантов: можно сохранить две полные окрестности. Для области slide сохраняется только выбранный слайд; для deck — вся презентация. Во время подготовки редактор доступен, состояние показано счётчиком `…/9`.

Попадание в кэш применяется сразу. Промах запускает запрос после 600 мс покоя; если этот вариант уже готовится, интерфейс ожидает тот же Promise, не дублируя запрос. Запросы отсутствующих вариантов действительно используют модель, поэтому первая подготовка увеличивает число платных генераций. Достигнутый эффект — быстрое повторное переключение, а не сокращение вычислений провайдера.

Ручная правка, смена фиксации, правка агентом и отмена создают новую ревизию с текущим содержанием как `base` и очищают устаревший кэш. Смена варианта ревизию не меняет. Все варианты одной ревизии строятся из одной базы, чтобы последовательное переключение не накапливало перефразирование. Запоздалые ответы предыдущей ревизии или другого проекта отбрасываются.

При исчерпании квоты localStorage интерфейс показывает ошибку сохранения и позволяет скачать backup. Серверного хранилища и синхронизации устройств пока нет.

## Чат

`POST /api/v1/presentations/chat` получает единый снимок: текущий deck, параметры области, альтернативы и историю диалога. Backend сам собирает контекст модели. Поэтому агент всегда получает альтернативные тексты, а не только названия настроек.

Ответ модели: `message` и `content` либо null для ответа без правок. Backend проверяет область, уникальность ID, сохранение зафиксированных слайдов и числовые источники графиков. Правки выбранного слайда не могут затронуть остальные. Для всей презентации разрешены добавление, удаление и перестановка слайдов. Названия и абзацы зафиксированных слайдов сохраняются сервером. Валидный результат применяется атомарно и добавляется в историю отмены; ошибка сохраняет текущую презентацию и текст запроса для повтора.

## Следующий этап при серверном хранении — предложение

Тот же контракт можно перенести на сервер без изменения контекста агента:

| Таблица | Назначение |
| --- | --- |
| `projects` | Владелец, название, текущая ревизия, выбранные параметры |
| `project_sources` | Исходные материалы и их извлечённый текст |
| `project_revisions` | Снимки содержания и связь с предыдущей ревизией |
| `text_variants` | `project_id + revision_id + scope + slide_id + settings_key`, текст, модель, версия промпта, статус, время |
| `chat_messages` | Сообщение, роль, время, связанная ревизия, применённая правка |

Один серверный сборщик `buildAgentContext(projectId, scope, slideId)` должен читать исходники, текущую ревизию, варианты этой ревизии и диалог. Модели не нужен прямой SQL-доступ. Для контроля конкурирующих правок сервер должен принимать ожидаемый `revision_id` и возвращать конфликт, если проект уже изменён. Эти таблицы и серверное хранение пока не реализованы.
